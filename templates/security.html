Security & Data Protection

A short, honest summary of where our security posture stands today — written for the Board, not for a compliance filing.

{{ org }} is currently a working demo — not yet the production system that will hold real case files.

Before any real case data is entered, we've designed and pressure-tested a protection model built for how sensitive this work is:

  • Four staff access levels, including a time-limited, individually named "Restricted-Case Reviewer" tier for domestic-violence-survivor and at-risk-minor cases.
  • Two-factor authentication enforced at the database level, not just the login screen.
  • Built-in safeguards so no staff member can grant themselves access to restricted files.
  • A separate, encrypted storage model for the most sensitive case records.

Reporter protections — CAPTCHA, anonymous reporting, and fast-tracked routing for high-risk tips — are part of the same design.

This model has already been through one round of adversarial internal security review, which is exactly how it's supposed to work: found and fixed before anything gets built, not discovered after.

Where Things Stand Today

Today's demo still has a few known configuration items open, including a photo-storage setting that's more permissive than it should be. We're closing those before this becomes the production system — this demo does not yet hold real case data, so the immediate risk is low, but we're not treating that as a reason to leave it unfixed.

Security here is being designed in from day one — reviewed and fixed before launch, not patched on after.
